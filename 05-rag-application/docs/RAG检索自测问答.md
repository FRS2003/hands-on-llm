## 一、检索管线核心问答

### 1.1 BGE-M3 / FAISS / Milvus / FLAT / IVF / HNSW — 四层概念辨析

四个概念经常被混在一起说，但其实各管各的层：

```
你问: "DINOv2在医学影像中有什么优势？"
              │
   ┌──────────┼──────────┐
   │          ▼          │
   │   BGE-M3 翻译官     │  ← 第1层：Embedding 模型
   │   文字 → 1024个数字  │     把问题变成向量
   │       ↓             │
   │  [0.23,-0.45,...]   │
   │          │          │
   │          ▼          │
   │  FAISS / Milvus     │  ← 第2层：向量数据库
   │  图书馆              │     存向量 + 搜向量
   │          │          │
   │  ┌──────┼──────┐    │
   │  ▼      ▼      ▼    │
   │ FLAT  IVF   HNSW    │  ← 第3层：索引类型
   │ 逐本翻 分区  导航    │     怎么最快找到最像的
   └─────────────────────┘
```

**第1层：Embedding 模型（翻译官）— BGE-M3 vs OpenAI Embedding**

| | BGE-M3 | OpenAI text-embedding-3 |
|------|--------|------|
| 维度 | 1024 | 3072 |
| 语言 | 100+ 语言，中英跨语言原生 | 英文为主 |
| 成本 | 本地免费 | 按 token 计费 |
| 部署 | GPU 推理，~5ms/条 | API 调用，有网络延迟 |
| 可控性 | 可量化、加速、微调 | 不可控 |

**第2层：向量数据库（图书馆）— FAISS vs Milvus**

| | FAISS | Milvus |
|------|-------|--------|
| 定位 | 向量搜索**库** | 向量**数据库** |
| 存储 | 本地文件（读入内存） | 服务端持久化 |
| 网络 | 无（进程内调用） | gRPC/HTTP API |
| 适用规模 | < 100 万向量 | 100 万 ~ 10 亿 |
| 多用户 | ❌ 单机 | ✅ 多租户 |
| 类比 | 本地书架 | 在线图书馆管理系统 |

**第3层：索引类型（找书目录）— FLAT / IVF / HNSW**

同一个问题的三种解法——"38 个向量里怎么最快找到最像的那几个"：

```
FLAT（暴力搜索）:
  查询向量和 38 个论文向量逐一算距离 → 排序 → 取 Top-K
  复杂度 O(n)，n=38 时 <1ms
  ✅ 100% 精确  ❌ 向量多了就慢（线性增长）

IVF（倒排索引）:
  先把 38 个向量聚成 5 个簇（K-Means）
  查询时只搜最近的 2 个簇 → 只算 ~15 个向量
  复杂度约 O(√n)
  ✅ 比 FLAT 快  ❌ 近似（最佳匹配在未搜索的簇里就会丢）

HNSW（分层导航图）:
  像高速公路→主干道→小巷：上层节点少跳得快，下层节点多搜得细
  查询从最上层开始跳，每层找到最近邻后下降到下一层
  复杂度 O(log n)
  ✅ 大规模下最快  ❌ 构建索引慢、占内存多
```

**关键判断：为什么本项目用 Flat？**

38 篇论文，FLAT < 1ms。IVF 和 HNSW 的索引构建开销 > 搜索节省的时间。**当前规模下 Flat 就是最优解，换 HNSW 是负优化。** 这个判断力比"我会用 HNSW"更重要。

**易混点澄清：**

```
BGE-M3 和 FAISS 不是竞争关系 → 上下游（BGE-M3 产向量，FAISS 存向量）
FAISS 和 Milvus 是竞争关系  → 都做向量搜索，规模和复杂度不同
FLAT/IVF/HNSW 和 FAISS 不是并列 → FAISS 是数据库，IVF/HNSW 是 FAISS 里的索引选项
```

**FAISS 是库，Milvus 是服务（最核心的区别）：**

```
FAISS（进程内的库）:
  你的 Python 脚本
      ├─ import faiss
      ├─ index = faiss.read_index("faiss.index")   ← 从磁盘读到内存
      ├─ index.search(query_vec, k=5)              ← 进程内调用，<1ms
      └─ 脚本结束，索引从内存释放
  
  关掉 Python，FAISS 就不存在了。但磁盘上的 faiss.index 文件完好无损，下次启动时需要重新读取


Milvus（一直跑着的服务）:
  终端 1: $ milvus start          ← 服务常驻后台，一直在等请求
  
  终端 2: 你的 Python 脚本
      ├─ from pymilvus import connections
      ├─ connections.connect("localhost:19530")     ← 连到服务
      ├─ collection.search(query_vec, k=5)          ← gRPC 网络调用
      └─ 脚本结束，Milvus 服务还活着
  
  关掉 Python，Milvus 还在跑，下一个脚本接着用。
```

**什么时候必须换 Milvus：**

| 场景 | FAISS 能行吗 |
|------|:---:|
| 38 篇论文，个人用 | ✅ 完美 |
| 10 万篇，多个人同时查 | ⚠️ 每个人都要加载索引到内存 |
| 100 万篇 + 每天新增 500 篇 + Web 服务 7×24 | ❌ 无持久化、无增量插入、无多用户 |
和 Word 文档一个道理——关掉 Word，文档还在磁盘上，下次打开就好了。区别是 FAISS 不做增量更新，新增论文后需要重建索引（本项目中由 rebuild_m3.py 完成）。Milvus 做的是 Word 不关也能往里加内容，多人同时编辑也不冲突
一句话：FAISS 是 `import` 进来的库，Milvus 是 `connect` 过去的服务。38 篇论文没必要起一个服务。

### 1.2 FAISS 粗排 Recall 65%，Reranker 后 85%，数学上怎么成立的？

- 65% 是 FAISS 单独取 Top-5 时的 Recall@5
- 85% 是 FAISS 取 Top-20（oversample）→ Reranker 筛至 Top-5 后的 Recall@5
- Reranker 贡献来自两方面：① 精排准确（踢噪声）② 允许粗排放宽（无 Reranker 不敢取 20）
- 详见同目录《RAG 技术详解》第 7 章

### 1.3 Reranker 到底是什么？和 Embedding 模型的区别？

- Embedding（Bi-Encoder）：查询和文档分别编码，向量内积算相似度。快但交互浅
- Reranker（Cross-Encoder）：查询和文档拼接后一起过 Transformer，输出一个分数。慢但精确
- 一句话：Embedding 回答"像不像"，Reranker 回答"能不能回答问题"

### 1.4 七轮优化只有一轮有效，说明了什么？

- 数据质量 > 模型能力：英文原文摘要替换中文翻译是唯一有效优化
- 全文编码（458 碎片向量）反而降 Recall：信号碎片化
- 链式系统的瓶颈在最弱一环：Reranker 升级无效因为粗排才是瓶颈

### 1.5 为什么全文编码效果反而比摘要差？

- 信号碎片化：22 块碎片中只有 1 块含查询关键词，其余 21 块在向量空间中稀释了信号
- 38 个摘要向量（高信号密度）> 458 个全文碎片（低信号密度）

### 1.6 Query Expansion 为什么帮了 FAISS 却害了 Reranker？

- FAISS 向量检索受益于扩展关键词（更丰富的语义覆盖）
- Reranker 交叉编码器对噪声敏感——噪声关键词让它关注错误维度
- 解决：QE Split（搜索用扩展查询，Reranker 用原始查询）恢复到 85% 但未超越

### 1.7 系统的降级策略是什么？无 Reranker 时召回率多少？

降级链路：
```
正常: FAISS Top-20 → Reranker Top-5    Recall@5 = 100%, ~4s
高负载: 跳过 Reranker, FAISS 直接 Top-5   Recall@5 = 68.4%, ~100ms
极端: 返回预计算缓存                      ~1ms
```

**网格搜索细节（58 题，6 档权重，均无 Reranker）：**

| 向量权重 | BM25 权重 | Recall@5 |
|:---:|:---:|:---:|
| 0.9 | 0.1 | **68.4%** ← 最优 |
| 0.7 | 0.3 | 65.8% |
| 0.6 | 0.4 | 66.7% |
| 0.5 | 0.5 | 64.9% |
| 0.3 | 0.7 | 63.2% |
| 0.1 | 0.9 | 59.6% ← 最差 |

三个结论：
1. **向量是主心骨，BM25 是辅助。** BM25 主导时 Recall 暴跌至 59.6%，向量主导时为 68.4%
2. **权重不敏感。** 极端值之间仅差 9 个百分点——当前知识库规模下检索管线鲁棒，调权重不是优化重点
3. **Reranker 才是真正的杠杆。** 6 档权重调来调去最高 68.4%，加 Reranker 后 100%（+32pp）。优化精力放在 Reranker 而非权重调参

降级不是关服务，是主动用质量换延迟，保证服务还活着。原始评测日志见 `evaluation/results/` 目录（含 21 题与 58 题两份对照记录）

### 1.8 微调和 LoRA 的区别？什么时候用哪个？

**微调：修改全部参数**
```
原始 BGE-M3:  [w1...w567M]  5.67 亿参数全部训练
微调后:       [w1'...w567M'] 每个参数都变了
```

**LoRA：只训练旁路小矩阵**
```
原始 BGE-M3:  [w1...w567M]  冻结，一个不改
旁路:          A(567M×8) × B(8×567M)  ~900 万参数，<2%
```

| | 全量微调 | LoRA |
|------|---------|------|
| 训练参数 | 5.67 亿 | ~900 万 |
| 显存需求 | 24GB+ | 8-12GB |
| 存储 | 完整副本（2.17GB） | 旁路矩阵（~35MB） |
| 灾难性遗忘 | 风险高 | 风险低（原权重冻结） |
| 多任务 | 每任务一个副本 | 多个 LoRA 插件共存 |

**类比：** 全量微调 = 送到英国住三年（口音思维全变，可能忘了中文）。LoRA = 每天背 20 个医学术语（中文不变，需要时切换到术语模式）。

**和 RAG 项目的关联：** 理论上可以用医学文献三元组微调 BGE-M3，但当前 100% Recall 下边际收益有限。数据质量优化（英文原文替换中文翻译）的 +5pp 收益已经说明数据 > 模型。如果做，LoRA 是更合理选择——12GB 显存就能跑，且不破坏 BGE-M3 的多语言能力。
