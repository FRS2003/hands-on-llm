## 1. 项目概述

### 1.1 业务背景

VSD（室间隔缺损）是最常见的先天性心脏病，基于超声心动图进行亚型分类是临床难点。本项目构建了一个基于 RAG（Retrieval-Augmented Generation）技术的文献智能助手，覆盖 38 篇 VSD/超声心动图/深度学习领域论文，支持中英文自然语言查询，自动检索相关文献并生成带引用的 AI 回答。

### 1.2 为什么选 RAG 而不是微调？

| 对比维度 | RAG | 微调（Fine-tuning） |
|---|---|---|
| 知识更新 | 增删论文即更新，无需重训 | 需要重新训练模型 |
| 可解释性 | 返回引用来源，可溯源 | 黑盒生成，无法溯源 |
| 成本 | 按 API 调用计费 | 需要 GPU 训练资源 |
| 幻觉控制 | 基于检索结果约束生成 | 容易编造不存在的内容 |
> **文档定位：** 一份可复现的 RAG 系统从零搭建教学文档，面向想动手学会"检索增强生成"全链路的学习者

对于 38 篇论文的规模，实际上可以全量塞进 LLM 上下文窗口（38 × 5000 字 ≈ 190K tokens），但为了**学习 RAG 技术栈**和**展示工程能力**，选择了 RAG 路线。

### 2.1 RAG 核心流程详解

**问题：一个中文问题是如何变成带引用的回答的？**

```
Step 1: 用户输入 "DINOv2在医学影像中有什么优势？"
         │
Step 2: BGE-M3 将问题编码为 1024 维向量
         │  [0.023, -0.451, 0.782, ..., 0.134]  ← 1024 个浮点数
         │
Step 3: 在 FAISS 向量库中搜索最相似的 Top-20 个文档块
         │  使用余弦相似度（向量内积，因为 L2 归一化后等价）
         │
Step 4: BGE-Reranker 对这 20 个候选重新打分
         │  交叉编码器：同时输入 (查询, 文档) → 输出相关度分数
         │  FAISS 粗排只看全局语义，Reranker 看细粒度匹配
         │
Step 5: 按论文去重，取 Top-5
         │
Step 6: 构建提示词 → DeepSeek 生成回答 → 流式返回
         │  "根据 [1] DINOv2 论文，该方法在自然图像上..."
         │
Step 7: 前端展示回答 + 可展开的论文来源卡片
```

### 3.3 向量化（Embedding）

**为什么选择 BGE-M3？**

| 模型 | 维度 | 大小 | 特点 |
|---|---|---|---|
| BGE-small-zh-v1.5 | 512 | 133MB | 仅支持中文 |
| BGE-M3 | 1024 | 2.17GB | 支持 100+ 语言，中英文跨语言 |
| text-embedding-3-large | 3072 | API | 付费，延迟高 |
| multilingual-e5-base | 768 | 278MB | 轻量多语言，但质量不如 BGE-M3 |

**选择 BGE-M3 的原因：**
- 原生支持**中文查询 → 英文文档**的跨语言检索
- 1024 维向量比 512 维有更强的语义表达能力
- 可以在 GPU 上本地运行，零成本

**编码代码：**

```python
from sentence_transformers import SentenceTransformer
import numpy as np
import faiss

# 加载模型（首次自动从 HuggingFace 下载 2.17GB）
model = SentenceTransformer("BAAI/bge-m3", device="cuda")

# 编码文档
texts = ["Title: DINOv2... Abstract: Self-supervised visual foundation model..."]
embeddings = model.encode(texts, batch_size=16, show_progress_bar=True)
embeddings = np.array(embeddings).astype("float32")

# L2 归一化（使内积 = 余弦相似度）
faiss.normalize_L2(embeddings)

# 构建 FAISS 索引
dim = 1024
index = faiss.IndexFlatIP(dim)  # IP = Inner Product（内积）
index.add(embeddings)
```

## 4. 检索系统选型与设计

### 4.1 为什么 FAISS 而不是其他向量数据库？

> **文档定位：** 一份可复现的 RAG 系统从零搭建教学文档，面向想动手学会"检索增强生成"全链路的学习者
|---|---|---|---|
| **FAISS** | 极快（ms 级），纯 Python/C++，免费 | 无持久化内置，需手动 save/load | 小规模（<100K 向量） |
| ChromaDB | 自带持久化，API 友好 | 需要 Python 3.9+，依赖重 | 中规模项目 |
| Milvus | 分布式，支持十亿级 | 部署复杂，需要 Docker | 企业级 |
| Pinecone | 全托管，零运维 | 付费，数据在云端 | 不想管运维 |

**选择 FAISS 的理由：** 38 篇论文 → 38~72 个向量，FAISS 完全够用。且 FAISS 是 Meta 开源的工业级库，理解 `IndexFlatIP`、`IndexIVFFlat`、`IndexHNSWFlat` 的区别与选型依据是掌握向量检索的基础。

### 4.2 两阶段检索：粗排 + 精排

```
查询 → FAISS 粗排（Top-20, ~1ms）
           │
           ▼
       Reranker 精排（Top-5, ~50ms）
           │
           ▼
       最终结果
```

**为什么需要两阶段？**

- **FAISS（双编码器）：** 查询和文档各自独立编码为向量 → 向量相似度搜索。**快但不精确**，因为查询和文档在编码时没有交互。
- **Reranker（交叉编码器）：** 同时输入 (查询, 文档) → 输出一个相关度分数。**慢但精确**，因为查询和文档进行了深度交互。

两阶段本质上是一个效率-精度的 tradeoff：
- 第一阶段：从 38 篇中快速筛选 20 篇候选（精确度 ~65%）
- 第二阶段：对 20 篇候选逐一精细评分（精确度提升到 85%）

**代码实现：**

```python
from sentence_transformers import CrossEncoder

# 加载 Reranker（交叉编码器）
reranker = CrossEncoder("BAAI/bge-reranker-base", device="cuda")

# 粗排：FAISS 搜索 Top-20
q_emb = embedder.encode([query]).astype("float32")
faiss.normalize_L2(q_emb)
scores, indices = index.search(q_emb, 20)  # 返回 Top-20

# 精排：Reranker 对每个候选重新打分
pairs = [(query, texts[idx]) for idx in indices[0]]
rerank_scores = reranker.predict(pairs)

# 按精排分数重排序
candidates.sort(key=lambda x: x["rerank_score"], reverse=True)
```

### 4.3 嵌入模型 vs Reranker 的区别

这是检索系统里最容易混淆的一组概念。

| | 嵌入模型（Bi-Encoder） | Reranker（Cross-Encoder） |
|---|---|---|
| 代表模型 | BGE-M3 | BGE-Reranker-base |
| 输入 | 单个文本 → 一个向量 | (查询, 文档) 对 → 一个分数 |
| 编码方式 | 查询和文档独立编码 | 查询和文档在注意力层交互 |
| 速度快 | 极快（预计算向量，搜索时只算查询） | 慢（每对都要重新过一遍模型） |
| 精确度 | 较低（无交互） | 较高（深度交互） |
| 典型用法 | 粗排（Top-K 筛选） | 精排（Top-K 重排序） |

**一句话总结：** 嵌入模型回答"这两个东西像不像"，Reranker 回答"这篇文章能回答这个问题吗"。

## 5. 七轮优化全记录

### 5.1 优化总览

```
版本                              FAISS粗排  +Reranker  = 最终    有效？
──────────────────────────────────────────────────────────────────
① V5CN 中文翻译                      70%    →   80%    =  80%    起点
② 英文摘要补全（Semantic Scholar）     65%    →   85%    =  85%    ✅ +5%
③ v2 Reranker 升级                   70%    →   80%    =  80%    ❌
④ PMC 全文编码（21篇 × 5000字）       70%    →   80%    =  80%    ❌
⑤ Query Expansion（关键词扩展）       75%    →   80%    =  80%    ❌
⑥ BM25 + 向量混合搜索                70%    →   85%    =  85%    =
⑦ LLM 全文总结（DeepSeek 生成摘要）    70%    →   80%    =  80%    ❌
```

> ⚠️ 解读说明：
> - "FAISS粗排"列 = 无 Reranker 时，FAISS 直接取 Top-5 的 Recall@5
> - "+Reranker"列 = FAISS 先取 Top-20（oversample）→ Reranker 精排筛至 Top-5 后的 Recall@5
> - Reranker 的贡献来自两方面：① 精排准确（把混进 20 的噪声踢掉）+ ② 允许粗排放宽（无 Reranker 时不敢搜 20 篇，噪声会跟着进最终输出）
> - 各轮 benchmark 测试集不完全相同，不同轮之间的百分比不能直接横向对比

### 5.2 逐轮分析

#### 第一轮：V5CN 中文翻译（80%）

**做法：** 用 BGE-small-zh-v1.5 模型，将英文论文翻译成中文后编码。

**问题：** 翻译质量参差不齐，专业术语翻译不准确。

#### 第二轮：英文摘要补全（85%）✅ 唯一有效

**做法：** 切换到 BGE-M3（支持中英文跨语言），通过 Semantic Scholar API 获取 21 篇论文的英文原文摘要，arXiv API 获取 15 篇，手动构造 2 篇。

**为什么有效？**
- BGE-M3 的 1024 维向量比 BGE-small 的 512 维有更强的语义区分能力
- 英文原文消除了翻译误差
- 跨语言检索：中文查询 → 英文文档，BGE-M3 原生支持

#### 第三轮：v2 Reranker 升级（80%）❌

**做法：** 将 BGE-Reranker-base（278MB）替换为 BGE-Reranker-v2-m3（1.5GB，更强的交叉编码能力）。

**为什么无效？**
- 瓶颈在 FAISS 粗排（65% 召回率），不在 Reranker 精排
- Reranker 再强，如果正确答案根本没进 Top-20 候选池，Reranker 也无能为力
- **核心洞察：检索系统是链式结构，最弱的一环决定上限**

#### 第四轮：PMC 全文编码（80%）❌

**做法：** 从 PubMed Central 获取 21 篇论文的 XML 全文（每篇 5000 字），分块编码为 458 个向量。

**为什么无效？（这是最重要的教训）**

```
摘要编码：38 个向量，每篇论文 1 个高质量向量
全文编码：458 个向量，每篇论文 ~22 个碎片向量

问题：一篇论文的 22 个碎片中，只有 1 个包含查询关键词。
      其余 21 个在向量空间里和别的论文竞争，压制了正确碎片。
```

**关键概念 —— 信号碎片化（Signal Fragmentation）：**

"局限性"这个词在 Cheng 2024 论文全文里只出现 1 次。全文拆成 22 块后，只有 1/22 的向量包含这个信号。在 458 个向量的竞争池里，这个信号被稀释了。

**这里可以进一步思考"语义分块 vs 固定长度分块"的差别。**

#### 第五轮：Query Expansion（80%）❌

**做法：** 用 DeepSeek 将中文查询扩展为英文关键词 → FAISS 用扩展后的查询搜索 → Reranker 用扩展后的查询重排。

**关键发现：**
- FAISS 粗排从 65% 提升到 75%（✅ 扩展查询让关键词更丰富）
- Reranker 精排从 85% 降到 75%（❌ 噪声关键词干扰了 Reranker 的判断）

**改进尝试 —— "QE Split"（搜索用扩展查询，Reranker 用原始查询）：**

```
搜索：扩展查询 → FAISS → Top-20（丰富关键词帮助召回）
重排：原始查询 → Reranker → Top-5（干净查询保持精度）
结果：恢复到 85%，但未超越
```

**洞察：Reranker 对查询质量非常敏感。噪声关键词会让它关注错误的语义维度。**

#### 第六轮：BM25 + 向量混合搜索（85%）

**做法：** 手动实现 BM25 关键词匹配 + FAISS 向量匹配，加权融合。

```python
combined_score = 0.6 × FAISS_score_normalized + 0.4 × BM25_score_normalized
```
**两路结果怎么合：加权融合 vs RRF**

双路召回各产出一份排序，常见的合并方式有两种：

| 融合方式 | 做法 | 特点 |
| --- | --- | --- |
| **加权融合（本项目采用）** | 先把两路分数各自归一化到同一量纲，再按固定权重相加：`0.6×向量 + 0.4×BM25` | 保留"谁分高、高多少"的信息，权重可调；前提是两路分数必须先归一化到可比尺度 |
| **RRF（倒数排名融合）** | 不看具体分数，只看文档在每路里的**名次**，按 `Σ 1/(k+rank)` 累加后重排 | 不需要分数归一化、对分数尺度不敏感、开箱即用；代价是丢弃了分数差距信息 |

本项目知识库规模小，两路分数都能稳定归一化，因此选用权重可控的加权融合（以向量语义为主、BM25 精确锚定为辅）；RRF 更适合"两路分数量纲差异大、难以归一化"的大规模工业场景。二者没有绝对优劣，取决于分数是否可比。

**结果：** 持平 85%。BM25 帮助了一些关键词精确匹配的场景，但整体提升被 Reranker 吞掉了。

#### 第七轮：LLM 全文总结（80%）❌

**做法：** 用 DeepSeek 对 21 篇 PMC 全文生成 3-5 句的结构化摘要。

**为什么无效？（最有价值的洞察）**

LLM 把所有论文总结成了**统一的语言模板**：
- "This study addresses..."
- "The method employs..."
- "Key results include..."

所有论文的向量开始趋同，区分度下降。**在向量检索中，语义多样性 > 内容丰富度。**

**这与直觉相反：** 通常认为 LLM 总结 = 提取精华 = 更好的检索，但实际上 LLM 的"规范化"写作风格让每篇论文失去了独特性。

## 6. 关键技术决策与对比分析

### 6.1 全文编码 vs 摘要编码

| 维度 | 摘要编码 | 全文编码 |
|---|---|---|
| 向量数量 | 38（每篇 1 个） | 458（每篇 ~22 个） |
| 信号密度 | 高（精华浓缩） | 低（碎片化） |
| 查询匹配 | 差（部分关键词缺失） | 好（关键词覆盖全） |
| 向量区分度 | 高（每篇独特） | 低（碎片互相压制） |
| Recall@3 | 65% | 70% |
| 最终（+Reranker） | **85%** | 80% |

**结论：** 在小规模知识库（<100 篇）场景下，**高质量摘要 > 全文分块**。

### 6.2 为什么不做 Fine-tuning？

自然会有一个疑问：为什么不用"微调 + RAG"的混合方案？

**主要基于四点考虑：**
1. 38 篇论文的规模太小，微调会过拟合
2. RAG 天然支持知识库更新（加一篇论文只需重新编码，不需要重训）
3. RAG 输出可溯源引用，学术场景对此有强需求
4. 项目目标是学习 RAG 工程能力，不是追求极致性能

## 7. 检索系统深度原理

> 这一章深入讨论检索系统选型中最关键的四个问题，每个都结合本项目的实际验证结果展开。

### 7.1 FAISS 索引类型：Flat vs IVF vs HNSW

FAISS 提供多种索引类型，核心区别在于**精度-速度-内存**的 tradeoff。

#### IndexFlatIP（本项目使用）

```
原理：暴力搜索。查询向量与数据库中每个向量逐一计算内积。
复杂度：O(n × d)，n=向量数量，d=维度
精度：100%（精确搜索，不丢失任何结果）
内存：n × d × 4 字节（38 × 1024 × 4 = 156KB）
```

> **文档定位：** 一份可复现的 RAG 系统从零搭建教学文档，面向想动手学会"检索增强生成"全链路的学习者

#### IndexIVFFlat（倒排索引 + 平面编码）

```
原理：用 K-Means 将向量空间聚类为 c 个簇（Voronoi 单元）。
      查询时只搜索最近的 nprobe 个簇，而不是全量。
复杂度：O(nprobe × n/c × d)，近似 O(√n)
精度：95-99%（取决于 nprobe 参数）
内存：Flat + 聚类中心额外开销
```

**类比：** 图书分类法。查询"深度学习"时只去计算机科学书架（1 个簇），不去文学书架。

**关键参数：**
- `nlist`（簇数量）：越大精度越高但越慢，通常设为 `4 × √n`
- `nprobe`（搜索簇数）：越大精度越高但越慢

#### IndexHNSWFlat（分层可导航小世界图）

```
原理：构建多层图结构。底层包含所有向量，上层是稀疏采样。
      搜索时从顶层开始，贪婪地向最近邻移动，逐层下降。
复杂度：O(log n × d)，近似对数级
精度：98-99.9%
内存：最高（需要存储图结构，约 n × M × 4 字节额外开销）
```

**类比：** 高速公路网。顶层 = 跨省高速（快速逼近目标区域），底层 = 城市道路（精确到达目的地）。

#### 三种索引对比

| | IndexFlatIP | IndexIVFFlat | IndexHNSWFlat |
|---|---|---|---|
| 搜索速度 | O(n) | O(√n) | O(log n) |
| 精度 | 100% | 95-99% | 98-99.9% |
| 内存 | 最低 | 中等 | 最高 |
| 是否需要训练 | 否 | 是（K-Means） | 否 |
| 参数调优 | 无 | nlist, nprobe | M, efSearch |
| 本项目适用 | ✅ 38 向量 | ❌ 过度设计 | ❌ 过度设计 |

**延伸：什么时候应该从 Flat 升级到 IVF 或 HNSW？**

> 当向量数量超过 ~50K 时，Flat 的线性搜索开始成为瓶颈。10 万向量，Flat 每次查询 ~50ms，HNSW 只需 ~0.5ms。对实时性要求高的场景（如在线客服、搜索引擎），这是必须的升级。

### 7.2 纯向量检索够用吗？要不要混合关键词检索？

这是一个**被本项目的实验数据直接回答**的问题。

#### 纯向量检索的缺陷

向量检索通过语义相似度工作。1024 维向量压缩了整个文本的语义，在这个过程中**精确信息会丢失**：

```
问题："Cheng 2024 的局限性是什么？"
向量搜索：匹配到了讨论 "AI模型局限性" 的论文 [35]（分数 0.45）
         而 Cheng 2024 论文 [12] 排在第 21 位（分数 0.32）
         → Cheng 2024 被淹没在 "局限性" 相关的向量海洋里

关键词搜索（BM25）：直接命中 "Cheng 2024" →"limitations"
         → Cheng 2024 论文排在第 3 位
```

**向量检索 vs 关键词检索的根本区别：**

| | 向量检索 | 关键词检索（BM25） |
|---|---|---|
| 匹配方式 | 语义相似度 | 词频 + 逆文档频率 |
| "Cheng 2024" | 被稀释在 1024 维向量中 | 精确命中 |
| "数据泄漏"和"data leakage" | ✅ 自动跨语言匹配 | ❌ 需要同义词表 |
| "DL模型的心血管疾病诊断" | ✅ 语义理解长查询 | ❌ 词袋模型丢失语序 |

> **💡 BM25 是什么？**
>
> BM25（Best Matching 25）是信息检索领域最经典的关键词匹配算法，可以理解为 **TF-IDF 的升级版**。
>
> **核心思想：** 一篇文档和查询的相关度 = 查询中每个词对该文档的"重要性"之和。
>
> ```
> BM25(查询, 文档) = Σ IDF(词) × TF(词在文档中的频率)
> ```
>
> - **TF（词频）：** 这个词在这篇文档里出现了多少次。出现越多越相关，但有上限（防止 100 次和 1000 次拉开的差距过大）。
> - **IDF（逆文档频率）：** 这个词在整个文库中有多"稀有"。如果一个词 38 篇论文里只出现 1 次（如 "EchoNet-Dynamic"），它天然具有极高的区分度，命中即找到。
>
> **为什么 BM25 能和向量检索互补？**
>
> 向量检索（BGE-M3）把 "Cheng 2024 limitations" 压缩成一个 1024 维向量，在这个过程中 "Cheng" 这个精确信号被稀释了。BM25 不做任何压缩，直接匹配字符串 "Cheng" → 看到哪篇论文包含 "Cheng" 就给高分。这在查询包含**人名、专有名词、缩写（如 DINOv2）**时极其有效。
>
> 这就是上表中 "Cheng 2024" 在向量侧"被稀释"但在 BM25 侧"精确命中"的原因——两者处理信息的方式完全不同，天然互补。

**结论：向量 + 关键词混合 = 互补。**

#### 本项目混合搜索的实现与结果

```python
# 分数融合（加权求和）
combined_score = 0.6 × FAISS_score_normalized + 0.4 × BM25_score_normalized
```

**实验数据：**

```
FAISS only（纯向量）  : 13/20 = 65.0%
混合（FAISS + BM25）  : 14/20 = 70.0%    ← 粗排提升 5%
混合 + Reranker       : 17/20 = 85.0%    ← 最终持平（Reranker 吃掉了差异）
```

在粗排阶段，BM25 确实提供了额外的信号（+5%）。但经过 Reranker 精排后，这个增益被抹平了——因为 Reranker 本身在一定程度上弥补了向量检索的词汇盲区。

**延伸：在大规模场景下还需要混合检索吗？**

> 需要，而且更重要。当知识库从 38 篇扩展到 38 万篇时，纯向量的粗排精度会进一步下降（更多干扰向量），BM25 的精确匹配能力成为保障最低召回率的关键。工业界（Google、Bing）全部使用混合检索，向量负责语义覆盖，关键词负责精确锚定。

### 7.3 Query Expansion 有没有必要？

这个问题需要分两个阶段回答：**粗排阶段有必要，精排阶段有副作用。**

#### 本项目的实验数据

```
场景                         FAISS粗排  Reranker后
────────────────────────────────────────────────
原始查询                      65%   →   85%
QE扩展（粗排+精排都用扩展）    75%   →   80%  ← 粗排↑ 精排↓
QE Split（粗排扩展/精排原始）  75%   →   85%  ← 粗排↑ 精排不变
```

#### 为什么 QE 帮助粗排但伤害精排？

**粗排（双编码器）：** 查询和文档独立编码。扩展查询 → 更多关键词 → 向量更"丰满" → 更容易命中相关文档。

**精排（交叉编码器）：** 查询和文档深度交互。扩展查询 → 引入噪声词 → Reranker 被噪声词分散注意力 → 误判。

```
原始查询："Cheng 2024 的局限性"
扩展后："limitations methodology shortcomings Cheng et al 2024 congenital heart disease study"

Reranker 看到 "methodology shortcomings" → 开始关注论文的方法论缺陷
→ 给讨论"AI方法论缺陷"的论文打了高分 → 真正的 Cheng 2024 论文排名下降
```

#### 什么时候 QE 有价值？

| 场景 | 是否需要 QE | 原因 |
|---|---|---|
| 短查询（<5 词） | ✅ 需要 | 向量太稀疏 |
| 跨语言查询 | ✅ 需要 | 桥梁作用 |
| 专业术语查询 | ✅ 需要 | 术语映射 |
| 已经清晰的查询 | ❌ 不需要 | 引入噪声 |
| 精排阶段 | ❌ 不需要 | 干扰交叉编码 |

**延伸：在大模型时代，Query Expansion 还有必要吗？**

> QE 本身可以用 LLM 实现（本项目用的 DeepSeek），但核心不是"用不用 LLM 做 QE"，而是**QE 的结果用在哪里**。本项目的关键发现是：QE 应该只用于粗排，精排必须用原始查询。这是一个通用的设计原则，与 QE 的具体实现方式无关。

### 7.4 粗排的意义：能不能只用 Reranker？

**这是一个非常常见的误区：既然 Reranker 更准，为什么不一上来就用它？**

#### 答案：延迟。纯粹的 Reranker 方案不可行。

```
38 篇论文 × 每对编码 ~50ms = 1.9 秒/查询（纯 Reranker）
                         vs
FAISS Top-20 筛选（1ms）+ 20 对 Reranker（1 秒）= 1 秒/查询（两阶段）
```

在 38 篇规模下差异是 ~1 秒。但如果知识库有 10 万篇：

```
10 万篇 × 50ms = 5000 秒 = 1.4 小时/查询（纯 Reranker）→ 完全不可用
FAISS Top-100（10ms）+ 100 对 Reranker（5 秒）= 5 秒/查询（两阶段）
```

#### 粗排做的是什么？

粗排本质上是一个**门控机制（Gating Mechanism）**。它不提供最终答案，但它决定 Reranker 能看到什么。

```
粗排 = 世界杯小组赛（38 支 → 20 支晋级）
精排 = 淘汰赛（20 支 → 5 支胜出）
```

**关键约束：** 如果正确答案在小组赛就被淘汰了（没进 Top-20），Reranker 永远看不到它。这就是为什么本项目中 Reranker 升级（base → v2）没用——瓶颈在小组赛的出线率（65%），不在淘汰赛的裁判水平。

#### 粗排召回率 vs 最终召回率

Reranker 让粗排可以"放心搜更多"。代码逻辑（app_v2.py）：

```python
# 无 Reranker: FAISS 直接输出 Top-5
retrieve(query, top_k=5)                          # Recall@5 = 65%

# 有 Reranker: FAISS 先取 Top-20（oversample），Reranker 筛回 Top-5
retrieve(query, top_k=5, oversample=20)           # Recall@5 = 85%
```

Reranker 贡献的 +20pp 来自两个因素的叠加：

| 贡献来源 | 原理 |
|---------|------|
| **精排准确** | 把混进 20 里的噪声踢掉，保证最终 5 篇质量 |
| **允许粗排放宽** | 无 Reranker 时只敢取 5 篇（多取 = 噪声进最终输出），有了 Reranker 敢于取 20 篇，正确论文进候选池的概率大幅提升 |

**Reranker 间接提升了召回——不是因为它能在不存在的地方找到答案，而是因为它让粗排有底气去更宽的候选池里捞。**

以 Agent 项目的统一 benchmark（58 题，同一测试集）上的严格对照实验为例：
- 纯向量 + BM25 混合检索：Recall@5 = **68%**
- 混合检索 + Reranker（粗排 20 → 精排 5）：Recall@5 = **100%**
- Reranker 贡献：**+32pp**

**关键约束仍然成立：** 如果正确答案连 Top-20 都没进，Reranker 也无能为力。第 3 轮 Reranker 升级无效（v2 model 没有提升 Recall）就是因为瓶颈在粗排的候选池覆盖范围（oversample 数量、embedding 质量），不在精排的判别力。

**关键结论：** Reranker 的价值不只是精排——它让粗排敢于放宽搜索范围，间接提升了召回；但它救不了没进候选池的文档。

### 7.5 双索引架构的泛化：数据没有摘要怎么办？

本项目的双索引设计（摘要索引 → 粗排 + 全文分块索引 → 精排）依赖于学术文献的天然结构：每篇论文自带摘要。但如果数据是产品文档、客服记录、新闻文章——没有摘要，怎么建 Index A？

**核心原则不变：Index A 需要高信号密度的向量来快速缩小候选，Index B 需要细粒度向量做精确匹配。** 区别只是 Index A 的向量从哪来。

| 数据类型 | Index A（粗排锚点）来源 | Index B（精排块）来源 |
|---|---|---|
| 学术论文 | 论文自带摘要 | 全文分块 |
| 产品文档 | 文档标题 + 第一段（概述） | 正文按 `##` 标题分块 |
| 客服记录 | LLM 生成一句话总结 | 完整对话记录 |
| 新闻文章 | 标题 + 导语（前 150 字） | 正文段落分块 |
| 代码仓库 | README.md 或模块 docstring | 函数/类级代码块 |
| 法律合同 | 条款标题列表 | 逐条正文 |
| 无结构文本 | LLM 逐段生成概述 | 原文段落 |

**最通用的兜底方案：LLM 逐段生成概述作为 Index A。** 用 DeepSeek 给每个 chunk 生成一句概述，这句概述的向量放进 Index A，原文 chunk 放进 Index B。成本：100 万篇文档 × 50 token ≈ $3。

**本项目实验结论的直接迁移：**

1. **第 5 轮教训（PMC 全文分块导致召回下降）：** Index A 的向量**质量 > 数量**。LLM 生成的概述比盲目分块的碎片更适合做粗排。
2. **第 7 轮教训（LLM 总结导致向量趋同）：** 如果 LLM 把所有概述写成了统一模板，区分度会下降。生成概述时必须**保留原文关键实体词**（产品名、订单号、错误码），而不是用通用语言重写。
3. **第 6 轮结论（BM25 混合提升粗排 5%）：** 如果数据中有可精确匹配的字段（订单号、产品 SKU、API 名称），应该再加独立一路 BM25 索引做精确召回。

## 8. 常见疑问辨析（FAQ）

### Q1: 为什么 BGE-M3 比 OpenAI Embedding 好？

**答：**
- **成本：** BGE-M3 本地免费，OpenAI Embedding 按 token 计费
- **多语言：** BGE-M3 原生支持 100+ 语言，OpenAI 的中文嵌入质量一般
- **可控性：** 本地模型可以调参、量化、加速
- **维度：** BGE-M3 的 1024 维在大多数场景下足够，OpenAI 的 3072 维性价比不高

### Q2: 你的两阶段检索为什么不用 Milvus？

**答：**
- 38 篇论文用 FAISS 完全够，Milvus 是为百万级以上设计的
- FAISS 是 Meta 开源的，理解各索引算法原理（Flat、IVF、HNSW 的区别）并能说明选型理由，比单纯换一个向量数据库更重要
- 如果扩展到 10 万篇论文，会选择 Milvus + IVF 索引

### Q3: RAG 系统中的幻觉（Hallucination）怎么控制？

**答：**
- **检索约束：** 只让 LLM 基于检索到的 Top-5 论文回答，提示词中明确要求"只根据提供的论文内容回答"
- **引用标注：** 要求 LLM 用 [1][2] 标注引用，用户可以点开验证
- **置信度阈值：** 如果 Top-1 论文的相似度 < 0.3，提示用户"没有找到相关论文"

### Q4: 如果检索结果中有一篇不相关的论文排在前面怎么办？

**答：**
- 这就是 Reranker 存在的意义——FAISS 粗排可能误判，Reranker 交叉编码能纠正
- 如果 Reranker 也误判（相似度分数很高），说明这篇论文的语义确实和查询相关，可能是相关但用户不熟悉的内容
- 长期方案：加入用户反馈机制（点赞/踩），用反馈数据微调 Reranker

### Q5: 为什么全文编码没有提升 RAG 效果？

**答：** 这个问题值得展开，原因有三：

三个原因：
1. **信号碎片化：** 全文分块后，关键信息被稀释在多个碎片中，每篇论文内部碎片互相竞争
2. **向量空间拥挤：** 458 个向量中找 Top-20，单篇论文的 22 个碎片互相压制，正确答案的碎片可能排在第 21 位
3. **粗排瓶颈：** FAISS 的向量相似度是基于整体语义的，而不是关键词匹配。一个包含"局限性"的碎片在向量空间里和其他片段没有显著区别

**改进方向：** 混合索引（摘要向量做粗排锚点 + 全文向量做精排补充），但在这个规模下收益有限。

## 9. RAG 关键技术专题

> 以下专题补充正文中未充分展开的 RAG 核心技术问题，每个都附本项目可关联的实验数据。

### 9.1 RAG vs 长上下文 LLM：有了 1M Token 窗口还需要 RAG 吗？

这是近年很受关注的话题：Gemini 2.0 支持 2M token、GPT-5 支持 256K token——如果把论文全塞进上下文窗口，还需要检索吗？

**直接塞进去会发生什么？**

```
38 篇论文 × 5000 字/篇 ≈ 190K tokens
→ 完全在 256K 窗口内，技术上可行

但：
- 每次查询都传 190K tokens → API 费用 = 查询 × 0.19M × $0.14/M = $0.027/次
  如果每天 100 次查询 → $2.7/天 → $80/月
  同等 RAG 方案：BGE-M3 免费 + DeepSeek 只传 Top-5（~5K tokens）→ $0.001/次
  **成本差 27 倍**

- 即使 LLM 声称支持 256K，实际的"有效注意力"远小于窗口大小
  Lost in the Middle 效应：窗口越大，中间部分越容易被忽略
  38 篇论文中的前 3 篇和最后 3 篇被重点关注，中间的 32 篇几乎被遗忘

- 延迟：190K tokens 的 prefill 需要 ~8 秒（H100），检索只需要 ~1 秒
```

**什么时候 RAG 仍然必要？**

| 条件 | RAG | 纯长上下文 |
|---|---|---|
| 知识库频繁更新（每天都有新论文） | ✅ 索引增量更新即可 | ❌ 每次重传全部 |
| 需要溯源引用 | ✅ 天然支持 | ⚠️ 需额外 prompt 约束 |
| 成本敏感（高 QPS） | ✅ 检索 + 小上下文 | ❌ 每次传全量 |
| 只需精确查找某条信息 | ✅ 检索直接定位 | ⚠️ 大海捞针 |
| 需要通读全库做综合分析 | ⚠️ 检索可能遗漏 | ✅ 全文在上下文里 |

**结论：长上下文和 RAG 不是替代关系，是互补关系。** 长上下文让 RAG 的 Top-K 可以更大（从 5 篇扩大到 20 篇），RAG 让长上下文不用每次都传全量。正确架构：RAG 把相关文档找出来 → 长上下文 LLM 在更大的候选集上做综合分析。

> **本项目的关联：** 38 篇论文恰好卡在一个尴尬的位置——全量塞得下但成本高、检索跑得通但召回率只有 85%。这恰好是讨论"RAG vs 长上下文"的理想案例：如果只查一次，RAG（85% 召回，低延迟）和全量上下文（100% 覆盖，高延迟）各有优劣；如果每天查 100 次，RAG 的成本优势碾压。

### 9.2 分块策略深度对比

本项目 Q6 只讲了"分块 vs 不分块"的结论，这里展开讲**怎么分**。

**五种分块方式，从简单到智能：**

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **固定长度** | 每 200 字切一块，重叠 50 字 | 实现简单 | 句子被截断，语义不完整 |
| **基于句子** | 按句号/换行切，凑到接近 chunk_size | 保持句子完整 | 段落上下文可能丢失 |
| **递归分块** | 先按段落切 → 还太大按句子切 → 还太大按词切 | 自适应 | 参数多，调优复杂 |
| **语义分块** | 用 Embedding 模型判断相邻句子的语义距离，距离突增处切 | 语义连贯 | 需要额外推理，慢 |
| **文档结构分块** | 按 Markdown 标题/PDF 章节层级切 | 保留文档结构 | 需要文档本身有结构 |

**本项目为什么最终选择了"不分块"？**

```
38 篇论文，平均摘要 1500 字 → 一个向量就能完整表达
分块后 458 个向量 → 每篇论文内部分块互相竞争 → Recall 反而下降

关键判断：chunk_size 应该根据数据的"信息密度"来定
  - 信息密度高（摘要、导语、结论）→ 小块（200-500 字）
  - 信息密度低（方法细节、引用列表）→ 大块（1000-2000 字）或不编码
```

**分块策略小结：** 分块不应使用固定参数，而要按数据的自然粒度来定：学术论文以摘要为自然单元不分块，长文档按 Markdown 标题层级切分。固定长度分块最容易实现但也最粗暴——本项目的实验数据表明，它在小规模场景下反而会降低召回率。

### 9.3 RAG 评估指标体系

本项目的 Recall@3 只衡量了检索阶段。一个完整的 RAG 系统需要两层评估：

**检索层指标（本项目做了的）：**

| 指标 | 含义 | 本项目实测 |
|---|---|---|
| **Recall@K** | 正确答案在 Top-K 中的比例 | Recall@3 = 85% |
| **MRR**（Mean Reciprocal Rank）| 正确答案排名的倒数均值，排名越靠前得分越高 | 未测（20 题样本太小，无统计意义） |
| **NDCG@K** | 考虑了排名位置的归一化折损累计增益 | 需要人工标注相关度（0-3 分），未测 |

**生成层指标（本项目没做，但工业界必做）：**

| 指标 | 含义 | 怎么算 |
|---|---|---|
| **Faithfulness（忠实度）** | 回答中的每句话是否都能在检索到的文档中找到支撑 | LLM 逐句检查，判断是否有"幻觉" |
| **Answer Relevancy（答案相关性）** | 回答是否切题 | 对回答反向生成问题，看和原问题的相似度 |
| **Context Precision（上下文精度）** | 检索到的文档中有多少是真正有用的 | 检索了 5 篇，只有 3 篇被答案引用 → 3/5 |
| **Context Recall（上下文召回）** | 答案中用到的信息，检索阶段是否都找到了 | 把答案拆成句子，逐句检查来源是否在检索结果中 |

**工具：** RAGAS 框架可以自动化计算以上四个指标，只需要 LLM API 调用不需要人工标注。适合大规模持续评估，但需要至少 100+ 条查询才有统计意义——本项目 20 题规模太小，手动抽查更合适。

### 9.4 Prompt 工程在 RAG 中的关键设计

Prompt 设计直接影响 RAG 的幻觉率、引用准确性和"我不知道"的诚实度。

**本项目实际使用的 Prompt 模板及其设计意图：**

```
你是 VSD（室间隔缺损）深度学习研究助手。
请根据以下论文内容回答用户问题。          ← ① 限定信息来源

对话历史：{history}                       ← ② 保持多轮对话连贯性

相关论文：                                ← ③ 标注引用编号
[1] DINOv2 (...) : ...
[2] EchoNet-Dynamic (...) : ...

用户问题：{query}

请用中文回答，标注引用来源如 [1][2]。    ← ④ 强制引用格式
如果论文无法回答，请如实说明。            ← ⑤ 允许说"不知道"
```

**每一条的设计意图：**

- ① **信息来源限定：** "根据以下论文内容"——如果不加这句，LLM 会用训练数据里的知识回答，绕过检索结果。这是 RAG 幻觉的第一来源。
- ④ **强制引用：** 要求 `[1][2]` 格式标注，用户可点击验证。引用本身是一种自我约束——LLM 编造的引用和原文对不上，可以被检测出来。
- ⑤ **允许不知道：** 这是最容易被忽略但最重要的一句。不加的话 LLM 会强行编一个答案。加了之后，当检索结果确实不相关时，LLM 更倾向于诚实。
- ③ **编号一致性：** Prompt 中 `[1]` 和来源展示中 `[1]` 必须一一对应。本项目的 bug 之一就是这里曾经过错位。

**进阶技巧（本项目了解但未实现）：**

- **Chain-of-Verification：** 生成回答后，让 LLM 再读一遍自己的回答，逐句核对引用是否正确，输出修正后的版本。
- **Few-shot examples：** 在 Prompt 中给 1-2 个"正确的引用回答示例"，让模型模仿引用风格。

### 9.5 增量更新：知识库变了怎么办？

本项目是一次性加载 38 篇论文建索引。但真实场景下知识库是活的——加新论文、撤旧论文、论文出了修订版。

**增（加新论文）：** 最简单。新论文编码 → 插入 FAISS 索引 → 完成。FAISS 支持 `index.add()` 追加向量，不需要重建整个索引。

**删（撤论文）：** FAISS 不支持直接删除向量。`IndexFlatIP` 只能重建——拿掉被删论文的向量，剩下的重新建索引。对于 38 篇的规模，重建耗时 < 1 秒。对于 100 万篇的规模，需要换 IVF 索引（支持按 ID 删除）或维护一个"删除列表"在搜索后过滤。

**改（论文更新）：** 本质是"删旧 + 增新"。如果更新频繁（每天几十篇），建议用 **双缓冲策略**——主索引提供服务，后台静默重建，建好后一键切换。

> **本项目的关联：** 7 轮实验每次都在重建索引——不是因为算法需要，而是因为摘要内容在变。这恰好证明了重建索引在小规模下成本极低，不需要复杂的增量方案。

### 9.6 RAG 失败的归因：责任在谁？100% 召回可能吗？

**问题一：RAG 回答不出来，应该怪 LLM 吗？**

不应该。RAG 是一个三级管线，每层独立归因：

```
用户问："Cheng 2024 有什么局限性？"
最终回答："没有找到相关信息"

失败归因：
  ├── 知识库层 ❌ → [12] 号论文摘要确实没写"limitations"这个词
  │     数据工程的问题。即使 LLM 是完美的，巧妇难为无米之炊
  │
  ├── 检索层 ❌ → 知识库有这篇论文，但 BGE-M3 向量相似度低于其他论文
  │     算法的问题。本项目的 Recall 天花板 ≈ 85%，15% 的查询天然会漏
  │
  └── 生成层 ✅ → LLM 正确地说了"无法回答"
        Prompt 里那句"如果论文无法回答请如实说明"生效了
        这是 RAG 系统的最低底线——可以答不出来，不能瞎编
```

LLM 在 RAG 中的责任只有一条：**诚实**。检索结果不相关时，它必须说"不知道"，而不是用训练数据里的知识去编一个听起来合理但实际不存在的答案。本项目的 Prompt 里有"如果论文无法回答，请如实说明"这句话——反复验证过，去掉这句，LLM 会自信地编造一个不存在的"局限性"。

**核心理解：** RAG 把 LLM 从"知识库"变成"翻译器"——LLM 不负责记住答案，只负责基于检索结果把答案讲清楚；检索不到的内容，就不应该编造。

**问题二：100% 召回率在工程理论上可能吗？**

不可能。不是算法不够好，是信息论层面的硬限制。

```
一篇摘要 5000 字 → BGE-M3 编码 → 1024 维向量 = 4096 字节

信息压缩比 ≈ 1000:1

没有一种压缩算法能在 1000:1 的压缩比下保证 100% 还原原文的每一个语义维度。
这是 Shannon 信息论的基本约束，不是工程问题。
```

具体到本项目的三个漏题，每道都是信息论问题而非算法问题：

| 查询 | 为什么召不回 | 根因 |
|---|---|---|
| "Cheng 2024 局限性" | [12] 摘要不写"局限"，写的是"However..." | 向量里没有"局限性"维度的信号，压缩丢失了一句话的语义侧面 |
| "VSD 公开数据集" | [10] EchoNet 是全宇宙最大的公开超声数据集，但摘要只写方法不写数据 | 同一篇摘要的"方法侧面"和"数据侧面"被压缩进了同一个向量，方法侧面占主导 |
| "不平衡分类 心脏病" | [14] 摘要只有 37 字符，信息量 ≈ 0 | 数据质量导致的零信息输入，任何模型都是垃圾进垃圾出 |

**83%-85% 是语义检索在小规模知识库上的工程上限。** Google 搜索几十年的优化也没有做到 100% 召回——不是因为工程师不够努力，是因为信息压缩和信息检索的数学本质决定了近似解是唯一解。追求 100% 是方向错误，正确的工程方向是：让系统在答不出来的时候**诚实地说"我不知道"**。
