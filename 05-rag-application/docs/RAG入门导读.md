## 📖 写在前面：你现在在哪里

大模型本身不会"查阅资料"——它的知识冻结在训练那一刻，也无法看到你手里的私有文献。**RAG（Retrieval-Augmented Generation，检索增强生成）** 的思路非常朴素：**先检索、后生成**——先从你的知识库里捞出最相关的几段材料，再让大模型只依据这些材料组织答案。

这份导读会带你沿着一个真实项目的演进顺序，回答六个层层递进的问题：

1. 为什么不能让大模型直接背下全部文献？
2. 关键词搜索（BM25）能解决什么、解决不了什么？
3. 向量检索为什么能"听懂语义"，又为什么会漏掉专有名词？
4. 两路检索都有了，结果怎么合？（本项目用加权融合，并解释为什么没用 RRF）
5. 合完为什么还要再过一道 Reranker？
6. 什么时候"一次检索"不够，需要会多步推理的 Agent？

**怎么读**：每节都按"为什么需要它 → 它是什么（配生活类比）→ 优缺点 → 对应本项目哪个代码文件"展开。看到 `代码：xxx.py` 就可以打开真实实现对照。

## 📚 术语对照表（先混个脸熟）

| 英文 / 缩写 | 中文叫法 | 一句话理解 |
| --- | --- | --- |
| Corpus | 语料 / 知识库 | 被检索的全部文档，本项目里是一批医学论文 |
| Chunk | 文本块 | 长文档切成的小段，是检索与嵌入的最小单位 |
| Embedding | 嵌入 / 向量表示 | 把一段文字映射成一串数字（向量），语义相近的文字向量也相近 |
| BM25 | 关键词匹配算法 | TF-IDF 的升级版，按"词频 + 稀有度"给文档打分 |
| Dense Retrieval | 稠密检索 | 用向量相似度做语义匹配，本项目用 BGE-M3 + FAISS |
| Hybrid Search | 混合检索 | 关键词路 + 向量路一起召回，再融合 |
| Fusion | 融合 | 把两路召回的两份排序合成一份（加权 / RRF 都是融合方法） |
| Reranker | 重排器 | 对粗排候选做"问题—文档"精配的 Cross-Encoder |
| Recall@K | 前 K 个里的召回率 | 正确文档是否出现在前 K 个结果中，本项目核心评测指标 |
| HyDE / QE | 假设文档 / 查询扩展 | 两种"改写查询以提升召回"的查询侧技术 |
| Agent（ReAct） | 智能体 | 通过"思考—调用工具—观察"多轮循环完成复杂任务 |

## 1. 为什么需要 RAG：把"闭卷考试"变成"开卷考试"

**生活类比**：直接问大模型，像让学生**闭卷考试**——它只能凭记忆作答，记不准就会"一本正经地编"（幻觉）。RAG 则是**开卷考试**：允许它先翻你指定的资料（检索），再照着资料答题，还能在答案里标注出处 [1][2]，读者可以点开核对。

相比"把所有文献塞进 Prompt"或"微调一个模型"，RAG 在**知识会更新、要求可溯源、文档规模中等**的场景最划算：新增一篇论文只需重新嵌入，不必重训；每个结论都能指回来源。这正是 [`RAG技术详解.md`](RAG技术详解.md) 第 1 章用对比表说明的选型理由。

## 2. 第一路检索：BM25 关键词匹配——"精确锚定"

**为什么需要它**：用户的问题里常有**专有名词、人名、缩写**，比如 "DINOv2"、"Cheng 2024"、"VSD"。这些字符串必须被**逐字命中**。

BM25 的直觉：一个词在某篇文档里出现得越多、而在整个语料里越稀有，它对这篇文档的贡献就越大。它是 TF-IDF 的实用升级版（带词频饱和与文档长度归一化）。

- ✅ 优点：精确、可解释、零模型成本，专名命中强；
- ❌ 短板：只认字面，"data leakage" 匹配不上"数据泄漏"，更理解不了长句语义。

**代码**：`evaluation/benchmark_hybrid.py` 里手写了一份 BM25（含 IDF、参数 k1=1.5、b=0.7），可以直接读到最朴素的实现。

## 3. 第二路检索：稠密向量——"语义模糊匹配"

**为什么需要它**：用户可能用和文档**不同的措辞**问同一个意思。向量检索先把每段文字用 Embedding 模型（本项目用 **BGE-M3**，1024 维、支持中英跨语言）编码成向量，再用 **FAISS** 计算"问题向量"和"文档向量"的距离，取最相近的若干篇。

- ✅ 优点：跨语言、跨措辞的语义匹配，"DL 模型的心血管诊断"能对上"deep learning for cardiac disease"；
- ❌ 短板：语义被压进 1024 维后，**精确信号会被稀释**——"Cheng 2024"可能淹没在一堆讲"局限性"的文档里（技术详解第 7.2 节有完整案例）。

**为什么用 FAISS 而不是 Milvus**：FAISS 是 `import` 进来的进程内**库**，Milvus 是要 `connect` 的常驻**服务**；本项目语料规模小，FAISS 的 Flat 暴力索引毫秒级返回且 100% 精确，上 IVF/HNSW 反而是负优化。

**代码**：`retrieval/build_dual_index.py`（粗/细双索引）、`retrieval/rebuild_m3.py`（BGE-M3 单索引最终版）。

## 4. 两路怎么合：加权融合，以及为什么没用 RRF

两路各给一份排序，融合常见两种：

| 融合方式 | 怎么做 | 适合什么情况 |
| --- | --- | --- |
| **加权融合（本项目）** | 两路分数各自归一化到同一尺度后加权相加：`0.6×向量 + 0.4×BM25` | 两路分数可比、想精细调控主次 |
| **RRF 倒数排名融合** | 不看分数只看名次，按 `Σ 1/(k+rank)` 累加 | 两路分数量纲差异大、难归一化时更省心 |

本项目规模小、分数能稳定归一化，因此选择**以向量语义为主（0.6）、BM25 精确锚定为辅（0.4）的加权融合**，而**没有使用 RRF**。网格实测 6 档权重 Recall 仅在 59.6%–68.4% 间波动（无 Reranker 时），说明这个规模下权重并不敏感——真正的杠杆是后面的 Reranker。

> ⚠️ 注意：早期 README 曾把融合误写成 "RRF"，以代码 `benchmark_hybrid.py` 与本文为准。两种融合的详细对比见技术详解第 7.2 节。

## 5. 为什么还要 Reranker：粗排与精排的两阶段

**生活类比**：在图书馆检索机上，关键词/语义搜索先**又快又全**地捞出 20 本"可能相关"的书（粗排，宁可多捞）；再由一位逐本翻看目录的馆员，从这 20 本里**仔细挑出**最贴题的 5 本（精排，宁缺毋滥）。

- **粗排（召回）**：Embedding 是双塔（Bi-Encoder），问题和文档各自独立编码、向量可预先算好，所以极快，但问题与文档没有深度交互；
- **精排（Reranker）**：Cross-Encoder 把"问题 + 候选文档"拼在一起过一遍 Transformer，让两者在注意力层充分交互，输出一个更准的相关性分数，代价是每对都要实时算、更慢。

正因为粗排快，我们才敢把候选池从 Top-5 放宽到 Top-20（oversample），给精排更大的挑选空间。本项目实测：FAISS 粗排 Recall@5 约 65%，放宽到 Top-20 再经 BGE-Reranker-base 精排到 Top-5 后提升到 85%（20 题原型阶段口径）。**关键约束**：如果正确文档压根没进粗排的 Top-20，再强的 Reranker 也救不回来——召回决定上限，重排逼近上限。

**代码**：`evaluation/benchmark_hybrid.py`（粗排 vs 加 Reranker 的三路对比）。

## 6. 查询侧优化：让"问题"本身更适合检索

检索质量不只取决于文档，也取决于**怎么问**。两种常见改写：

- **QE（Query Expansion，查询扩展）**：用 LLM 把简短中文问题补全成更丰富的中英文关键词。本项目发现它**帮了粗排却干扰了精排**（粗排 65%→75%，但扩展词噪声让 Reranker 从 85% 掉到 75%）；最终采用 **QE-Split：搜索用扩展查询、重排用原始查询**。
- **HyDE（Hypothetical Document Embeddings，假设文档）**：先让 LLM 针对问题"假装写一段答案"，再用这段假设答案去检索——因为"答案和答案"在向量空间里比"问题和答案"更接近。

**代码**：`evaluation/benchmark_qe.py`、`evaluation/test_qe_split.py`、`evaluation/test_hyde.py`，每个文件对应一次可复跑的消融实验。

## 7. 从 RAG 到 Agent：什么时候"一次检索"不够

单轮 RAG 适合**单一主题**：检索一次、生成一次，又快又稳。但当问题需要**跨主题、多步取证**（例如"对比两篇不相干论文在某指标上的差异"），就需要 Agent：它在 **ReAct 循环**里自己决定"下一步搜什么、读哪段、证据够不够、何时停"，把检索工具当成可反复调用的手。

本项目的实测对照（58 题、分三档难度，原始日志见 `evaluation/results/rag_vs_agent_58q.txt`）：

| 指标 | 单轮 RAG | ReAct Agent |
| --- | --- | --- |
| 完全命中（Rec 100%） | 58/58（100%） | 50/58（86%） |
| 平均 Recall | 100.0% | 94.5% |
| 平均耗时 | 一次检索 | 约 9 步循环 |

结论很有启发：**单主题问题上 RAG 又快又准，Agent 的价值在跨主题复杂任务**；而且 Agent 每多一步都可能引入偏差，需要 Harness（护栏、刹车、终止控制）来兜底——这部分正是第 ④ 模块「Agent 工程」的主题，可继续读 `04-agent/docs/`。
