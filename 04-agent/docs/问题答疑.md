# Agent 两步终止机制答疑：为什么最终答案不走 JSON？

> **所属模块**：第 ④ 模块「Agent 工程」，配合根目录源码与 [`Agent架构自测问答.md`](Agent架构自测问答.md) 阅读
> **前置知识**：了解 ReAct 循环、工具调用（Action / Observation）与 Harness Engineering 基本思想
> **文档定位**：把"两步终止（two-step termination）"这一设计的动机、成本与收益一次讲透，并给出可直接使用的面试参考回答

---

## 一句话结论

**Harness 把 Agent 的完整步骤历史（所有 Thought、Action、Observation）作为上下文，单独再调一次 LLM 来"重新组织"出最终答案，而不是让 Agent 在工具调用的 JSON 参数里直接携带长答案。** 最终答案不是凭空生成，而是基于完整执行轨迹做的一次总结输出。

## 一、第二步 LLM 调用的输入是什么？

```text
Step N : Agent 调用 submit_result(signal=true)
         ↓ 只传一个信号、零文本
Harness 检测到终止信号
         ↓
Step N+1: Harness 构造一个新 Prompt，内容是：

         "以下是一个研究 Agent 的完整工作过程：

         Step 1: Thought: 我需要先搜 DINOv2 的医学实验
                 Action: search_papers("DINOv2 medical imaging")
                 Observation: 找到了 8 篇论文，paper [21] 排第一
         Step 2: Thought: 找到了 DINOv2，读摘要确认
                 Action: read_section(paper_id=21, section="abstract")
                 Observation: DINOv2 摘要提到 ImageNet、COCO 等数据集 ...
         ...
         Step 8: Thought: 证据足够了，可以回答了
                 Action: submit_result(signal=true)

         请基于以上过程，生成简洁、准确的最终答案。要求：
         1. 直接回答原始问题
         2. 引用相关论文编号
         3. 不超过 300 字"

         ↓
         LLM 输出最终答案（纯自然语言，不走 JSON）
```

关键点：**第二步 LLM 能看到 Agent 走过的完整路径**——搜了什么、读了什么、发现了什么，因此不是凭空写答案。

## 二、和"Agent 自己把答案塞进 JSON"有什么区别？

区别在于答案生成的**通道**不同：

| 对比项 | 一步终止（Agent 自己传答案） | 两步终止（Harness 单独生成） |
| --- | --- | --- |
| 答案走的通道 | JSON 参数的 summary 字段 | 纯自然语言输出 |
| 转义要求 | 必须严格 JSON 转义（引号、换行、反斜杠） | 零要求，自由书写 |
| 失败概率 | 长文本高概率转义失败 | 几乎不会失败 |
| 答案质量 | 受 JSON 格式约束，可能为格式牺牲内容 | 纯文本生成，可自由组织语言，通常更高 |

**核心逻辑：让模型做它擅长的事（生成自然语言），不要逼它做不擅长的事（严格 JSON 转义）。**

## 三、为什么 JSON 转义对长文本很难？

自回归模型一次输出一个 token，写长文本时它关注的是**语义连贯性**，而不是 JSON 语法。让它一边写 500 字分析、一边惦记"引号要转义、换行要转义"，两件事会互相干扰，长文本尤其容易崩。

两步终止把这两件事彻底拆开：

- **第一步做决策**（"我做完了，可以交了"）：只传一个信号、零文本；
- **第二步写答案**：纯自然语言，怎么顺怎么写，完全不用管格式。

## 四、Token 消耗会不会增加？

几乎不增加，甚至可能更少，算一笔账：

**一步终止：**

```text
System Prompt + History（含 8 步完整 Observation）+ 工具定义
→ 输出：JSON 格式的 submit_result（含 500 字答案，约 600 token）
```

**两步终止：**

```text
第 N 步 ：System Prompt + History + 工具定义
→ 输出：submit_result(signal=true)（约 30 token）
第 N+1 步：System Prompt（简化版）+ History（完整）+ "请生成答案"指令
→ 输出：500 字纯文本答案（约 500 token）
```

- **输入侧**：两者几乎一样，History 都是完整的；而第二步已经不需要工具定义（不再调工具），System Prompt 反而可以简化；
- **输出侧**：一步终止是"500 字 + JSON 壳"约 600 token，两步终止是"30 token 信号 + 500 字纯文本"约 530 token。

总账基本持平，两步终止甚至略少，因为第二步省下了工具定义的输入。

## 五、答案准确性会不会下降？

不会，反而可能更好，有三个原因：

1. **上下文完整**：第二步 LLM 能看到完整步骤历史，掌握的信息和 Agent 一样多，不会因为"传 JSON 时漏字段"而丢信息；
2. **可以专心写答案**：一步终止时模型要同时兼顾内容和 JSON 语法、注意力被分散；两步终止只需专注"怎么把答案说好"；
3. **便于附加质量约束**：第二步 Prompt 可以明确要求"结构化 / 分点 / 引用论文编号 / 不超过 300 字"。这些约束在 JSON 通道里会让格式更复杂、转义更易崩，在纯文本通道里却很好加。

事实上，很多生产级 Agent 框架都采用这一做法：**最后一步单独调一次 LLM 做"答案合成"**，而不是让 Agent 在工具调用里把答案带出来。

## 六、那为什么不每一步都单独生成？

因为**成本和延迟**。

两步终止只多一次 LLM 调用，而且发生在最后一步，成本增量可以忽略。但如果每一步都拆成"决策 + 生成"两次调用，成本和延迟都会翻倍，并不值得。

只有**最后一步的答案生成**值得这样拆——因为答案是给用户看的、质量要求最高、格式失败的代价最大（用户直接看不到答案）。中间步骤的工具调用参数短、格式简单、失败概率低，没有拆分必要。

## 七、面试参考回答

> "两步终止的核心，是把**'决策终止'和'生成答案'拆开**，让模型各做各擅长的事。
>
> 第一步，Agent 调用 `submit_result(signal=true)`，只传一个终止信号、不传文本。这一步模型只做决策——'我做完了，可以交了'，因为没有长文本，JSON 转义几乎不会失败。
>
> 第二步，Harness 检测到信号后，把 Agent 的完整步骤历史作为上下文，单独调一次 LLM 生成最终答案。这一步是纯自然语言输出、不走 JSON 参数通道，彻底避开转义问题；模型可以专心组织语言、不用惦记格式，答案质量通常更高。
>
> Token 消耗几乎不增加：历史上下文是一样的，只是把'JSON 壳里的答案'换成'纯文本答案'，而且第二步不再需要工具定义，输入还略少。
>
> 本质上这仍是 Harness Engineering 的思路——**承认模型在结构化输出上不可靠，然后用架构设计绕过去，而不是逼模型学会转义。**"

这个回答覆盖了原理、方案对比与成本分析，最后回扣 Harness Engineering 的核心思想，是一个完整的应答结构。
