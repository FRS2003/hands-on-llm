## 2. Agent 与 Harness Engineering

### 2.1 Harness Engineering 到底是什么？

- 用确定性代码接管 LLM 不可靠的四个环节
- 助推器：预搜索（Loop 前自动保底）+ LLM Router（自动分流）
- 护栏：防重复 Guard、搜索上限、阅读上限
- 刹车：Tool Curfew + 无进展检测 + max_steps 兜底
- 接管：submit_answer 只收 citations，Harness 单独合成答案

### 2.2 ReAct 循环和 Harness 是什么关系？

- ReAct = 引擎（怎么跑）：Thought → Action → Observation 循环
- Harness = 刹车+护栏+接管（什么时候停、怎么防止跑偏）
- 关系类比：ReAct 是发动机，Harness 是刹车系统、安全带、安全气囊
- 论证：v1→v3 换的是终止逻辑（从 Prompt 移到代码），循环本身始终是同一个

### 2.3 为什么 Agent 不会主动调用 submit_answer？

- 业界共性问题，并非本项目的设计失误
- LLM 两个输出通道：tool_calls（调工具）和 content（纯文本）
- 模型输出完整分析后"完成感"已满足，不再切换模式调工具
- 证据：ReAct 论文、AutoGPT、Claude Code 全部都有终止兜底

### 2.4 JSON 转义崩溃是模型能力问题吗？

- 部分是，但不全是。更准确是 LLM 做结构化输出的**架构性矛盾**
- 自回归生成（语义驱动）和 JSON 语法约束（语法驱动）在逐 token 生成中互相矛盾
- DeepSeek Chat 比 GPT-4 弱，但本质上有天花板
- 三条业界解决方案：约束解码、拆两步、后处理修复
- **拆两步真正拆的是什么：** 不是"写长文"和"包装 JSON"拆成两轮——长文本本身就可以是答案（MiniCode 的 100 字符阈值证明了这一点）。拆两步拆的是**结构化元数据**（论文 ID、文件路径）和**自然语言答案**——短 JSON 传元数据（安全），自然语言通道写答案（不受 JSON 语法约束）。两者走不同通道，各做各擅长的事
- Agent 项目的方案：`submit_answer` 只收 `citations: list[int]`（纯整数，零转义），Harness 从 `gathered_papers` 取摘要，单独调 LLM 生成纯文本答案

### 2.5 Agent v1→v2→v3 每代验证了什么假设？

- v1："详细 Prompt 规则可以引导 Agent"→ 局部有效，但不主动输出答案
- v2："去掉规则，Agent 自主规划"→ 完全失败，DeepSeek Chat 无自主规划能力
- v3："不改 Prompt，改 Loop"→ 100% Answer Rate，Harness Engineering 正确范式

### 2.6 RAG 和 Agent 什么时候用哪个？

- 单主题 → RAG 足够，效果相同，速度快 10 倍
- 跨主题（需从两个不相关论文池取证据）→ Agent
- LLM Router 自动分流，0 危险错误（保守策略：宁可浪费不丢论文）

### 2.7 ReAct 和 LangGraph 是什么关系？

**ReAct 是模式，LangGraph 是实现模式的一种工具。** 不在同一层：

```
模式层:   ReAct（Thought→Action→Observation 循环）
              ↑
实现层:   ┌──┴────────────┬──────────────┐
          │               │              │
     手写 while 循环   LangGraph     AutoGPT
     (手写循环)     (LangChain)   (BabyAGI)
```

- **ReAct**（Yao et al., ICLR 2023）：定义了 Agent 如何交替推理和行动——先想（Thought）、再做（Action）、再看结果（Observation）、再调整。一种**设计范式**，不是代码
- **LangGraph**（LangChain 团队，2024）：有状态图执行引擎。把 Agent 控制流建模为节点（LLM推理/工具执行/人工审批）+ 边（条件跳转/固定流转），支持 Checkpoint 持久化、子图嵌套

| | 手写 while 循环 | LangGraph |
|------|----------------|-----------|
| 复杂度 | ~250 行，完全透明 | 框架 DSL，需学习成本 |
| 灵活性 | 任何逻辑 if/else | 受图模型约束 |
| 持久化 | 无 | 内置 Checkpoint |
| 调试 | print 大法 | Graph Viz 可视化 |
| 适用 | 原型、理解原理 | 生产环境、长时运行 |

**形象理解：** ReAct 是菜谱，LangGraph 是按菜谱操作的智能料理机。手写一遍 while 循环、理解每一步为何这样设计之后，再看框架就能明白它的每个机制分别在解决什么问题。

## 3. MiniCode 架构设计

### 3.1 ToolRegistry 和 MCP 是什么关系？

- ToolRegistry（30 行）：单进程 dict 查表，工具调度器
- MCP：跨进程/跨语言/跨网络的工具协议（JSON-RPC + stdio/HTTP）
- 关系：ToolRegistry 是 MCP 思想的单进程最小化实现
- 理解要点：理解了单进程版，再看 MCP 就能明白它额外引入的网络层与协议层在解决什么问题

### 3.2 为什么记忆注入从预注入改成了按需检索？

- 预注入：top-3 记忆拼入 System Prompt 每步携带，不管是否相关
- 按需：load_memory(topic) 工具，Agent 需要时才调
- 和 Context Compression 的 [EXPAND:id] 占位思想一致：不相关不消耗预算

### 3.3 Worker 是真正意义上的 Agent 吗？

- 不是。四要素（自主规划、工具调用、终止判断、状态记忆）只满足其中两个
- 有工具调用 + 终止判断，但无自主规划 + 无状态记忆
- 更接近"能调工具的 Skill"，介于 Skill 和 Agent 之间

### 3.4 为什么日常 Coding 不用多 Agent？

- 拆解 + 执行 + 汇总 的 LLM 调用成本 > 单 Agent 直接执行
- 仅复杂任务拆解时作为可选扩展
- 子任务间有依赖时并行无意义
什么时候该用多 Agent？
1. **子任务没有依赖**——可以并行跑，不互相等结果
2. **工具权限不同**——有的只读、有的可写，需要隔离
3. **单个上下文装不下**——大任务拆开各管各的上下文

### 3.5 edit_file 为什么用 old_string/new_string 而不是行号？

- 行号在代码修改后会漂移
- old_string 精确匹配原文，找不到就报错，不静默失败
- 只替换第一次出现（replace count=1）

### 3.6 100 字符终止阈值是怎么定的？

- 经验值，零成本方案的最优解
- 短文本（30-60 字符）→ 中间思考；长文本（>100 字符）→ 最终分析
- 两边都有漏洞，但无额外 LLM 调用成本
- max_steps 兜底时回收被拒绝的短文本片段

### 3.7 Skill 二阶段路由为什么要分开？（省 Token 的具体计算）

- 全部 Skill 描述拼入 Prompt ≈ 2-4K tokens，每步都带着
- Stage 1 关键词粗召回零 LLM 调用，把 4→1-3 候选
- Stage 2 仅候选>1 时调 LLM，max_tokens=20（选名字，非推理）
- 大部分任务 Stage 1 就确定了，Stage 2 被跳过

### 3.8 上下文压缩为什么从旧到新？

- 最近信息最相关
- Agent 在 Step 7 更关心 Step 5-6 发生了什么，不是 Step 1 的完整文件内容

## 4. 安全与工程素养

### 4.1 为什么注入检测用正则而不是 LLM？业界正确做法是什么？

**核心认知：AI 安全的"不可能三角"——检测器不能被它要检测的东西攻破。**

```
正则:          不管语义，匹配 bytes → 永远不会被 prompt 注入
ML 分类器:     理解语义，但是纯分类模型 → 不能被注入（没有指令跟随能力）
LLM-as-judge:  理解语义，但本身是 LLM → 你注入的目标和检测器是同一种东西
```

**误区澄清：不用 LLM ≠ 只能靠正则。** 中间还有一个正确的答案——ML 分类器。

**三层方案对比：**

| | 正则 | ML 分类器（DeBERTa） | LLM-as-judge |
|------|:---:|:---:|:---:|
| 原理 | 匹配 bytes | 分类模型（无指令跟随） | 让 LLM 判断是不是注入 |
| F1 上限 | ~0.50-0.65 | **~0.85-0.91** | ~0.85-0.90（但可被绕过） |
| 被注入风险 | ✅ 零（不理解语义） | ✅ 零（不能跟随指令） | ❌ 本身就能被注入 |
| 语义绕过 | ❌ 容易被变体重写绕过 | ✅ 能理解语义变体 | ✅ 能理解语义变体 |
| 延迟 | <5ms | ~50ms | 500ms-2s |
| 成本 | 零 | GPU 推理 | API 费用 ×2 |

**业界共识（2025-2026）：多层纵深，检测与执行分离**

生产环境推荐的 5 层架构：

```
Layer 1: 结构验证          — 用户输入和系统指令用 ChatML/JSON 明确分隔，~0ms
Layer 2: 正则               — 拦截已知攻击短语、编码绕过，<5ms
Layer 3: ML 分类器（非 LLM） — 捕捉语义意图，DeBERTa/RoBERTa，~50ms
Layer 4: 上下文异常检测      — 角色偏移、字段异常、长度离群，<5ms
Layer 5: 输出策略验证        — 最终输出检查（域名/格式/敏感词），不等
```

**已公开的生产结果（金融/医疗/政府，8 个月）：**
- 45 次注入攻击拦截，0 成功绕过
- 0.8% 误报率，~120ms 总安全开销

**本项目方案在业界的定位：**

本项目只实现了 Layer 2（正则），客观说并不充分。但"不够"的原因**不是**因为应该换成 LLM——是因为缺少 Layer 3（ML 分类器）来做语义理解。正确的演进方向：正则 + DeBERTa 分类器，而非正则 + LLM。

**方案小结：** 当前实现是纯正则方案——成本低、可审计、零延迟；但正则 F1 上限约 0.50-0.65，对语义变体存在盲区。若投入生产，应再加一层 ML 分类器（DeBERTa 或 RoBERTa 微调），它理解语义却无法被注入（没有指令跟随能力）。业界共识是层纵深，每一层用最合适的工具，而不是把所有希望押在一层上。"

**为什么不是 LLM-as-judge（一个常见的追问是）：**
1. **"攻击者后手"问题**——你用 LLM 检测注入，攻击者就把绕过检测器 LLM 作为攻击目标。2025 年 10 月的一项研究用自适应攻击测试了 12 种防御，>90% 被绕过
2. **检测器本身可被注入**——这是循环悖论在现实中的表现
3. **成本和延迟翻倍**——每次调用都要额外走一次 LLM

**关键设计原则：检测权威和执法权威分离。** 正则和 ML 分类器负责检测（可以降级），预算限制、能力边界、工具白名单负责执法（不随攻击演化而退化）。即使检测被绕过，执法层面仍然限制了攻击半径。

### 4.2 SecurityFilter 为什么没接入主循环？

- 独立模块已测试（4 BLOCK / 1 PASS），逻辑完整
- 接入只需一行代码：工具执行前调 `check_tool_call`
- 当时重点在把 Agent 循环跑通，安全层管线化优先级排后
- 客观定位：架构设计完整、已独立验证通过，接入主循环只缺一次调用（工具执行前调 `check_tool_call`）

### 4.3 子 Agent 出问题会导致 Supervisor 阻塞吗？

- 会。当前同步顺序执行，无 timeout 保护
- LLM API 调用未设 timeout，Worker 卡住 Supervisor 也卡住
- 工程解决四层：超时+重试 → 熔断器 → 自适应监控 → 持久化队列+无状态Worker

### 4.4 安全审查的黑名单和白名单为什么要合并？

- 黑名单：10 条正则拦截已知危险（rm -rf、sudo 等）
- 白名单：路径限定工作区内、文件类型限定安全后缀
- 合并为 L1 操作边界控制：先放行已知安全，再拦截已知危险，中间地带触发告警
- 设计意图：并非碰巧有两个检查，而是有意采用"正向白名单 + 负向黑名单"两把锁

## 5. 通用追问

### 5.1 两个项目之间是什么关系？

- MiniCode 复用 Agent v4 的 Harness 架构思想（while 骨架 + API 调用方式平移），但终止条件、防重复对象、兜底策略全部按 Coding 场景重写
- 同一套 ~250 行代码跨两个完全不同的领域（学术文献 + 编码）
- 证明了 Harness 的通用性：确定性控制逻辑不依赖场景

### 5.2 为什么选择 DeepSeek 而不是 GPT-4？

- 成本
- 中文能力
- 实测了三模型（chat/v4-pro/reasoner）的能力边界

### 5.3 项目里最大的技术难点是什么？

不是某个 Bug 修不好，是**认知转变**——从"相信 Prompt 能控制一切"到"理解代码才是 Agent 可靠性的来源"。

**难点一：Agent 三代演进——从改 Prompt 到改 Loop**

v1 把终止规则全写在 Prompt 里（"找到论文就输出 FINAL_ANSWER"），答案率 20%。当时本能反应是"Prompt 写得不够好"，于是花大量时间调措辞、加示例。调了一整天，答案率涨到 60%，但剩余 40% 始终修不好。

v2 走了另一个极端——完全去掉规则，让 Agent 自主规划。结果 0%——DeepSeek Chat 不具备自主规划能力，Agent 无限搜索永远不停。

v3 才意识到**问题不在 Prompt，在架构**。LLM 是自回归模型，它的训练目标是预测下一个 token，不是判断"任务是否完成"。"什么时候停"是元认知问题，当前所有 LLM 都做不到可靠判断。所以终止逻辑不能写在 Prompt 里求模型执行——必须写在代码里强制模型遵守。v3 把终止逻辑搬到代码（submit_answer + Tool Curfew + 无进展检测），答案率直接从 60% 跳到 100%。

**这个难在哪？** 难在放下工程师的本能——遇到问题第一反应是调参数、改 Prompt、换模型。但真正的解决方向是和本能相反的：不改模型，改代码架构。不是"让 LLM 更聪明"，而是"假设 LLM 会犯错，用代码兜底"。

**难点二：JSON 转义崩溃——不是 Bug，是架构性矛盾**

两个项目都撞上了同一个问题，但解决程度不同。

Agent 调用 `submit_result(summary="500 字审查报告...")` 时 JSON 解析失败。表面看是 DeepSeek Chat 的 JSON 能力弱，但深挖下去发现是**自回归生成和结构化输出的根本矛盾**：

```
模型生成时在想: "分析清楚、逻辑严密"     ← 语义驱动
JSON parser 要求: 引号写成 \"、换行写成 \n  ← 语法驱动

这两件事在逐 token 生成中互相冲突——模型做不到先写完再回头加转义
```
这不是"换个模型就好了"的问题——GPT-4 虽然更好但也无法 100% 避免。业界三条路（约束解码、拆两步、后处理修复）都是绕过模型能力用确定性手段兜底。问题不在"模型不知道要做"，在"模型做不到"。当它生成到第 400 个 token、注意力窗口已经远离那段 JSON 规范提醒时，它当前唯一关心的是 "SQL 注入这个论点怎么写才能逻辑严密"——不是 "前面有个引号需要转义"。
自回归生成是单向的——token 一个一个往外蹦，没有回头修改的机会。语法约束（JSON 转义）和语义生成（写分析）在逐 token 生成中天然冲突。这不是 Prompt 的问题，是架构限制。所以业界才走了三条路——没人走"把 Prompt 写得更清楚"这条路，因为验证过了，走不通：
- **约束解码：** 实时校验输出直接屏蔽非法 token，需要推理侧框架改造，成本高
- **拆两步：** 拆分的是**结构化元数据**和**自然语言答案**——短 JSON 传元数据（论文 ID / 文件路径，安全），纯文本通道写答案（不受 JSON 语法约束）。不是"写长文"和"包装 JSON"拆开——长文本本身就可以是最终输出
- **后处理修复：** 正则+语法修复库做自动化矫正，碰到复杂嵌套结构成功率有限

**Agent 项目（学术文献）：拆两步，彻底解决。** `submit_answer` 只收 `citations: list[int]`（纯整数，零转义风险），Harness 检测到调用后从 `gathered_papers` 取标题摘要，单独调一次 LLM 生成最终答案——答案文本完全不经过 JSON 参数通道。

**MiniCode（Coding Agent）：走了另一条路。** Coding 的分析结论本身就是最终答案，不需要传结构化元数据——Agent 直接输出长文本，Harness 的 100 字符阈值直接接受为最终回答，完全不经过 JSON 通道。这正是"拆两步"思路的另一种体现：**当答案不需要和结构化元数据捆绑时，直接让模型输出纯文本就行，不需要拆。** 当前 `submit_result(summary=str)` 的 JSON 转义问题只在少数场景触发（Agent 强硬要用工具调用格式输出），大部分情况通过字符阈值绕开了。

**这个难在哪？** 难在区分"模型能力问题"和"架构性问题"。前者换模型能解决，后者换模型只是把失败率从 80% 降到 20%，永远不会到零。能区分这两类问题，才知道什么时候该换模型、什么时候该改架构。MiniCode 的长期方案思路已经有了，只是因优先级未实施——这不影响对问题本质的理解。

**难点三：全文编码反降 Recall——反直觉的数据教训**

38 篇摘要向量 Recall 比 458 篇全文碎片向量高。直觉是"信息越多越好"，但实际是"信号被稀释了"。一篇论文拆成 22 块后只 1 块含查询关键词，其余 21 块在向量空间中和别的论文竞争，把正确碎片压制了。

**这个难在哪？** 难在需要放弃直觉相信数据。"更多数据 = 更好效果"在大多数 ML 场景下成立，但在向量检索中数据质量 > 数据量。38 个高质量向量 > 458 个低质量向量——这个反直觉结论不是推理出来的，是跑出来的。

### 5.4 项目有什么可以改进的地方？

- MiniCode SecurityFilter 接入主循环
- 多 Agent 加超时保护
- RAG 增量索引（目前是重建式）
- Agent 语义缓存（避免重复 LLM 调用）
