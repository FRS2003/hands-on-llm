这个问题问得非常好 —— 戳中了 "两步终止" 方案的核心设计细节。我给你掰开揉碎了讲。
一句话答案
Harness 把 Agent 完整的步骤历史（所有 Thought、Action、Observation）作为上下文，单独调一次 LLM，让它基于这些信息 "重新组织" 出最终答案。
不是凭空生成，是基于完整的对话历史做总结输出。
详细拆解：第二步 LLM 调用的输入是什么
plaintext
Step N:  Agent 调用 submit_result(signal=true)
         ↓ 只传一个信号，零文本
Harness 检测到终止信号
         ↓
Step N+1: Harness 构造一个新的 Prompt，内容是：
         
         "以下是一个研究 Agent 的完整工作过程：
         
         Step 1: Thought: 我需要先搜 DINOv2 的医学实验
                 Action: search_papers("DINOv2 medical imaging")
                 Observation: 找到了 8 篇论文，paper [21] 排第一
         
         Step 2: Thought: 找到了 DINOv2，读摘要确认
                 Action: read_section(paper_id=21, section="abstract")
                 Observation: DINOv2 摘要提到了 ImageNet, COCO 等自然图像数据集...
         
         ...
         
         Step 8: Thought: 证据足够了，可以回答了
                 Action: submit_result(signal=true)
         
         请基于以上过程，生成一个简洁、准确的最终答案。
         要求：
         1. 直接回答原始问题
         2. 引用相关论文编号
         3. 不超过 300 字"
         
         ↓
         LLM 输出最终答案（纯自然语言，不走 JSON）

关键点：第二步 LLM 能看到 Agent 走过的完整路径。 它知道搜了什么、读了什么、发现了什么，不是凭空写答案。
那这样和 "Agent 自己把答案塞进 JSON" 有什么区别？
区别在于答案生成的通道不一样：
表格
	一步终止（Agent 自己传答案）	两步终止（Harness 单独生成）
答案走的通道	JSON 参数的 summary 字段	纯自然语言输出
转义要求	必须严格 JSON 转义（引号、换行、反斜杠）	零要求，随便写
失败概率	长文本高概率转义失败	几乎不会失败
答案质量	受 JSON 格式约束，模型可能为了格式牺牲内容	纯文本生成，模型可以自由组织语言，质量通常更高
核心逻辑： 让模型做它擅长的事（生成自然语言），不要让它做它不擅长的事（严格的 JSON 转义）。
JSON 转义为什么难？我之前讲过 —— 自回归模型一次输出一个 token，它在写长文本的时候关注的是语义连贯性，不是 JSON 语法。你让它一边写 500 字的分析报告一边惦记着 "引号要转义、换行要转义"，它做不好。
两步终止就把这两件事拆开了：
第一步：模型做决策（"我做完了，可以交了"）—— 传个信号就行，零文本
第二步：模型写答案 —— 纯自然语言，怎么顺怎么写，不用管格式
追问：那 Token 消耗会不会增加？
几乎不增加，甚至可能更少。
算一笔账：
一步终止的 Token 消耗：
plaintext
System Prompt + History（含 8 步完整 Observation）+ 工具定义
→ 模型输出：JSON 格式的 submit_result 调用（含 500 字答案）

两步终止的 Token 消耗：
plaintext
第 N 步：System Prompt + History + 工具定义
→ 模型输出：submit_result(signal=true) （~30 token）

第 N+1 步：System Prompt（简化版）+ History（完整）+ "请生成答案"指令
→ 模型输出：500 字纯文本答案

对比一下：
输入侧：几乎一样，因为 History 都是完整的，只是第二步的 System Prompt 可以简化（不需要工具定义了，因为不调工具了）
输出侧：一步终止是 500 字 + JSON 壳（约 600 token），两步终止是 30 token 信号 + 500 字纯文本（约 530 token）
总消耗差不多，甚至两步终止还少一点—— 因为第二步不需要传工具定义了，省了几百 token 的输入。
追问：那答案的准确性会不会下降？
不会，反而可能更好。 三个原因：
上下文完整。 第二步 LLM 能看到完整的步骤历史，信息和 Agent 自己掌握的一样多，不会因为 "传 JSON 的时候漏了什么" 而丢失信息。
模型可以专心写答案。 一步终止的时候，模型一边写答案一边还要惦记 JSON 格式，注意力被分散了。两步终止的时候，模型只需要专注 "怎么把答案说好"，质量通常更高。
可以加额外的质量要求。 第二步的 Prompt 里，你可以明确要求 "答案要结构化"、"要分点"、"要引用论文编号"、"不超过 300 字"。这些约束在 JSON 通道里很难加（加了更复杂，转义更容易崩），但在纯文本生成里很容易加。
实际上，很多生产级 Agent 框架都是这么做的 —— 最后一步单独调一次 LLM 做 "答案合成"，而不是让 Agent 在工具调用里把答案带出来。
追问：那为什么不每一步都单独生成？
因为成本和延迟。
两步终止只多了一次 LLM 调用，而且是最后一步，成本增加可以忽略。但如果每一步都拆成 "决策 + 生成" 两次调用，成本就翻倍了，延迟也翻倍，不值得。
只有最后一步的答案生成值得这么做 —— 因为答案是给用户看的，质量要求最高，格式失败的影响最大（用户看不到答案）。中间步骤的工具调用，参数短、格式简单，失败概率低，不需要拆。
总结成面试话术
如果面试被问到这个问题，你可以这么答：
**" 两步终止的核心思路是把 ' 决策终止 ' 和' 生成答案 ' 拆开，让模型各做各擅长的事。
第一步，Agent 调用 submit_result (signal=true)，只传一个终止信号，不传文本。这一步模型只需要做决策 ——' 我做完了，可以交了 '。因为没有长文本，JSON 转义几乎不会失败。
第二步，Harness 检测到信号后，把 Agent 的完整步骤历史作为上下文，单独调一次 LLM 生成最终答案。这一步是纯自然语言输出，不走 JSON 参数通道，完全避开了转义问题。而且模型可以专心组织语言，不用惦记格式，答案质量通常更高。
Token 消耗方面几乎不增加，因为历史上下文是一样的，只是把 'JSON 壳里的答案 ' 换成了 ' 纯文本答案 '，甚至因为第二步不需要传工具定义，输入还少一点。
本质上，这还是 Harness Engineering 的思路 ——承认模型在结构化输出上不可靠，然后用架构设计绕过去，而不是逼模型学会转义。"**
这个回答既有原理、有对比、有成本分析，最后还回扣到 Harness Engineering 的核心思想，面试官会很满意。
